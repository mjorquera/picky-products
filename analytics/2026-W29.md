## Notes

- Methodology: same fallback as W28 — Pinterest Analytics UI returned no scrapeable content via Claude in Chrome again this week (client-rendered, no text/DOM fallback). Pulled analytics directly via Pinterest API v5 (`GET /pins/{id}/analytics`, `IMPRESSION,OUTBOUND_CLICK,SAVE,PIN_CLICK`) for both a 7-day and 28-day window, across all 171 pins on all 7 boards (listed directly via `GET /boards` and `GET /boards/{id}/pins`, not sourced from Notion Pin IDs).
- **Methodology change from W28:** rather than filtering Notion's Distribution DB by "has a stored Pin ID" (which only covers 55 of 240 Published records), pins were pulled directly from Pinterest and matched back to Notion by title. This surfaced the Pin ID coverage gap noted in Flags and caught ~110 additional live pins that `analytics_sync.py` currently can't see.
- Total live pins grew from 157 (W28) to 171 this week (+14), matching the 14 pins published in the trailing 7 days — consistent with the 2 pins/day cadence.
- Hit the Pinterest API's per-minute analytics rate limit (60 req/60s) repeatedly during the pull (342 analytics calls for 171 pins × 2 windows); recovered by pacing requests across multiple retry cycles, no data lost — all 171 pins have 7d/28d figures with zero fetch errors.
- Notion Distribution DB and Products DB were queried directly via the Notion REST API using the existing `NOTION_TOKEN` in `.env` (same approach as `analytics_sync.py`), since the Notion MCP connector's `query_database_view` tools require a Business plan upgrade the workspace doesn't have.
- No Notion writes were made this run — analytics fields in the Distribution DB were not updated (that's `analytics_sync.py`'s job, and it currently only covers the 55 pins with a stored Pin ID).
